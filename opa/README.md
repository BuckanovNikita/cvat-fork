# Патч правил OPA: задачи (issues) внутри организации

`rules/issues.rego` и `rules/comments.rego` — копии правил CVAT `cvat/apps/engine/rules/`
с одной добавленной привилегией: **любой участник организации может выполнять любые
действия с issues этой организации** и с комментариями к ним.

Комментарии патчатся вместе с issues потому, что диалог issue в интерфейсе создаёт и
редактирует объекты ресурса `comments`: без этого «любые действия» упираются в отказ
при ответе в треде.

## Что изменено относительно upstream

В каждом файле — два минимальных дополнения:

1. Правило `allow`, разрешающее всё при совпадении организации:

   ```rego
   allow if {
       input.auth.organization.id == input.resource.organization.id
       organizations.is_member
   }
   ```

2. Ветка `filter` для участника организации возвращает org-wide Q-объект вместо
   выборки «только там, где я staff», иначе список issues остаётся урезанным даже
   при разрешающем `allow`.

Правила песочницы (`utils.is_sandbox`) не тронуты: вне организации доступ остаётся
прежним. Пользователь, у которого `organization.user.role == null`, доступа не получает.

## Как применить

Правила отдаёт OPA не напрямую: бандл собирается `cvat_server` из файлов
`cvat/apps/engine/rules/*.rego` и раздаётся по `/api/auth/rules`. Поэтому:

1. Скопировать `opa/` рядом с `docker-compose.yml` деплоя (туда же, куда и
   `docker-compose.override.yml` из корня репозитория — он монтирует эти файлы
   в `cvat_server` только для чтения).
2. `docker compose -p <project> up -d --force-recreate cvat_server` —
   пересоздание обязательно: `get_opa_bundle()` кеширован через `lru_cache`,
   старый бандл живёт в процессе до перезапуска.
3. Дождаться, пока `cvat_opa` заберёт новый бандл — опрос идёт по расписанию
   бандла (по умолчанию десятки секунд), etag меняется вместе с содержимым.

## Проверка

Файлы проверены `opa check --strict` и `opa eval` на версии OPA из compose-файла
(`openpolicyagent/opa:1.12.2`) вместе с `utils.rego` и `organizations.rego`:
участник организации получает `allow == true` на `view`/`update`/`delete`/`create@job`
при совпадении id организации, `false` — при несовпадении и при `role == null`.
