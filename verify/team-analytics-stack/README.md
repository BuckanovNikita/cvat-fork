# Тестовый стенд Team Analytics

Одноразовый CVAT v2.82.0 с аналитикой в собственном пространстве имён локального
кластера `docker-desktop`. Поднимается и удаляется одной командой; на нём проверяются
все тикеты Team Analytics (ADR 0003). Team Analytics работает внутри бэкенда CVAT
(ADR 0006): эндпоинты `/api/team-analytics/{status,overview,trends,list,details}` сервера и
воркер аналитики (`cvat-backend-worker-team-analytics`) из чарта, а также настройки
(`settings`, `settings/users`, `project-names`), на которые сервер отвечает сам из Postgres.
Отдельного сервиса, его маршрута в прокси и Ingress на стенде нет.

Team Analytics отвечает только администраторам. Все цифры проверки читают как `ta-admin`
(`stack_api.reader(org)`: администратор с выбранной организацией — её цифры, без
организации — весь экземпляр); владельцы, мейнтейнеры и исполнители только работают
(создают проекты и задачи, размечают, отправляют события), а на Team Analytics получают 403.

```bash
./build-server.sh                          # образы из текущей версии: cvat/server:v2.82.0-fork
./build-ui.sh                              # и cvat/ui:v2.82.0-fork
verify/team-analytics-stack/run.sh up      # поднять, загрузить данные, выполнить проверки
verify/team-analytics-stack/run.sh down    # удалить всё созданное (успешно и когда ничего нет)
verify/team-analytics-stack/run.sh cycle   # up, затем down (и когда up упал)
```

Это теги по умолчанию (`TA_SERVER_IMAGE`, `TA_UI_IMAGE` в `stack.env`); образы должны быть
собраны из проверяемой версии, иначе проверки политик, аналитики и страницы не пройдут.
Остальные подкоманды (`seed`, `check-worker`, `check-event`, `check-tracer`, `check-task-progress`,
`check-final`, `check-final-ui`, `load-volume`, `check-volume`, `check-policies`, `check-issues`,
`check-issue-policies`, `forward`, `status`, `preflight`, `build-chart`, `render`, `check-render`,
`check-bundle`, `render-proxy`, `seed-access`, `check-access`, `check-org-creation`, `check-settings`, `check-fixes`, `check-cross-org`,
`check-isolation`, `check-load`, `check-review`, `check-analytics-off`, `check-evidence`, `restore-chart`) описаны в шапке
`run.sh`; `preflight` выполняет всё, что `up` делает до первого изменения в кластере (проверку образа сервера,
`check-issue-policies` для обеих сторон, сборку чарта и проверку рендера с аналитикой и без
неё), и ничего не создаёт и не скачивает. Ручных шагов нет.

## Два стенда одного пользователя

Стенд определяют `TA_RUN_ID` (пространство имён `cvat-ta-it-<TA_RUN_ID>`, по умолчанию
`<TA_RUN_ID>` = `$USER`) и `TA_HOST_PORT` (адрес `http://localhost:<порт>`). Каталог состояния,
учёт `port-forward`, снимки экрана и адрес Grafana берутся из них; общий у всех стендов только
каталог сборки чарта, названный по содержимому чарта (одинаковая сборка, повторная
собранная рядом отбрасывается). Порт по таблице портов k8s-infra: 8490 — стенд по
умолчанию, 8491 — второй стенд того же пользователя. Второй стенд из другой рабочей копии:

```bash
TA_RUN_ID=fork TA_HOST_PORT=8491 verify/team-analytics-stack/run.sh up
TA_RUN_ID=fork TA_HOST_PORT=8491 verify/team-analytics-stack/run.sh down
```

Каждая команда этого стенда — с теми же двумя переменными. Без них команда относится к
стенду по умолчанию: `down` из другой копии без `TA_RUN_ID` удалит стенд по умолчанию, а не
свой. Занятый порт — отказ, чужой процесс не трогается. Учёт `port-forward` пространства имён
хранит и его порт: каждая подкоманда, которая обращается к стенду по HTTP, сначала проверяет,
что `localhost:<TA_HOST_PORT>` обслуживает `port-forward` именно этого пространства имён (его
аргументы называют пространство имён и порт, и он слушает этот порт), иначе останавливается с
объяснением. Так `TA_RUN_ID` без своего `TA_HOST_PORT` не направит `kubectl` в один стенд, а
HTTP в другой. Учёт, записанный прежним `run.sh` (без порта), не принимается: на уже
работающем стенде один раз выполните `run.sh forward` с его переменными — он остановит прежний
`port-forward` и запустит новый с полным учётом.

## Что нужно от машины

- Docker Desktop с включённым Kubernetes (контекст `docker-desktop`), `kubectl`, `helm` 3,
  `curl`, `python3`, `ss`, `setsid`. Рендер читает сам `kubectl`, судит `render_guard.py`
  (только стандартная библиотека Python); отдельного разборщика YAML не нужно.
- Тег выпуска upstream `v2.82.0` в локальном репозитории (`STOCK_TAG`, по умолчанию
  `v2.82.0`; репозиторий — дерево upstream с изменениями форка, ADR 0005): `up` и `preflight`
  берут из него стоковые политики для стоковой стороны матрицы прав
  (`check-issue-policies stock`).
- Доступ в сеть при первой сборке чарта и при каждом изменении чарта или `Chart.lock`:
  репозитории чартов зависимостей (charts.bitnami.com, helm.vector.dev,
  grafana.github.io, nuclio.github.io, helm.traefik.io); Docker Hub для одобренных
  образов. Grafana при каждом старте скачивает плагин ClickHouse; проверки от Grafana не
  зависят.
- Образы, которые `run.sh` скачивает сам, по одному и с `nice` (одобрены владельцем,
  список в `stack.env`, `TA_APPROVED_PULLS`): `apache/kvrocks:2.15.0`,
  `cvat/clickhouse:23.12.2-debian-11-r0`, `cvat/postgresql:15.2.0-debian-11-r0`,
  `redis:7.2.11`, `grafana/grafana:10.1.5`, `busybox:1.36.1`. Стокового `cvat/server:v2.82.0`
  в списке нет: образ сервера форка от него больше не зависит. Рендер, в котором он есть, —
  отказ установки. Базовые образы сборки скачивает `./build-server.sh`, не `run.sh`.
- Образы, которые должны уже быть локально (никогда не скачиваются): образ сервера форка
  (`TA_SERVER_IMAGE`, полная сборка дерева `./build-server.sh` из публичных базовых образов,
  ADR 0006 и 0007; на нём работают сервер, все воркеры, включая воркер аналитики, и
  инициализатор; без него `up` и `preflight` останавливаются первым же шагом, до сборки чарта и
  до кластера; там же, в одноразовых контейнерах без сети, проверяется, что это Debian 12,
  `python3` в `PATH` — 3.12, а бандл политик, который собирает его сервер, с аналитикой и без
  неё совпадает с политиками дерева: `verify/policy_bundle.sh check` и `check-analytics`),
  `openpolicyagent/opa:1.12.2` и `timberio/vector:0.26.0-alpine` (`TA_LOCAL_IMAGES` в
  `stack.env`), прокси `nginx:1.27-alpine` (`TA_PROXY_IMAGE`) и образ UI (`TA_UI_IMAGE`,
  собирается `./build-ui.sh`). Любой другой образ в рендере чарта — отказ установки: список
  образов рендера — ровно одобренные, `TA_LOCAL_IMAGES` и три образа выше.
- Для проверки страницы — headless Chrome (`TA_BROWSER_BIN`, по умолчанию `google-chrome`)
  и Node.js 22 или новее.
- Свободный порт хоста (`TA_HOST_PORT`: 8490, для второго стенда 8491), зарезервированный в
  таблице портов k8s-infra. Занятый порт — отказ, чужой процесс не трогается.

## Что создаётся

- Пространство имён `cvat-ta-it-<TA_RUN_ID>` (по умолчанию `<TA_RUN_ID>` = `$USER`) с
  меткой `app.kubernetes.io/managed-by=cvat-fork-team-analytics-stack`, `ResourceQuota` и
  `LimitRange` (`namespace.yaml`). Пропавшее пространство создаётся заново; старше
  `TA_MAX_REUSE_HOURS` (36 ч) — пересоздаётся, потому что чистильщик кластера удаляет
  пространства через 48 ч. Созданное до последнего перезапуска кластера тоже пересоздаётся:
  чистильщик удаляет и такие. Время перезапуска стенд берёт из последнего прохода
  чистильщика (`restart_at` в ConfigMap `last-run` пространства `infra-janitor`, по
  k8s-infra); оно может отставать на один проход, а если его не прочитать, действует только
  правило возраста. `run.sh status` показывает, создано ли пространство до перезапуска.
  Чужое пространство с тем же именем не трогается.
- Метка владельца у всех стендов одна, поэтому стенды различаются только по `TA_RUN_ID`:
  без своего `TA_RUN_ID` `up` из другой копии обновляет релиз стенда по умолчанию, её `down`
  его удаляет (раздел «Два стенда одного пользователя»).
- Релиз чарта CVAT из импорта (`cvat/helm-chart` и компонент `cvat/components/analytics`,
  на который ссылается его `analytics`) со значениями `values.yaml`: аналитика включена,
  из воркеров только utils, webhooks и воркер Team Analytics
  (`cvat-backend-worker-team-analytics`, `run worker team_analytics`, три процесса по
  умолчанию чарта); сервер, все воркеры и инициализатор работают на образе сервера форка
  (`TA_SERVER_IMAGE`). Обновление итогов — периодическая задача CVAT раз в минуту
  (`cvat.apps.team_analytics.jobs.refresh_totals`; её ставит в очередь rqscheduler воркера
  utils, расписание записывает `syncperiodicjobs` инициализатора), выполняет её воркер
  аналитики. Настройки приложения — переменные окружения всех подов бэкенда
  (`cvat.backend.additionalEnv`): `TEAM_ANALYTICS_REFRESH_INTERVAL_S` = `TA_REFRESH_INTERVAL_S`
  (60 с, чтобы обновление было видно скоро). Переменной `TEAM_ANALYTICS_TECHNICAL_ACCOUNTS`
  больше нет: список технических учётных записей задаёт загрузка через API настроек (ниже,
  «Учётные записи»). Helm собирает зависимости в копии чарта в
  рабочем каталоге `${XDG_CACHE_HOME:-~/.cache}/cvat-fork/team-analytics/` (`TA_CACHE_DIR`;
  импорт не меняется), каталог сборки назван по хешу файлов чарта и `Chart.lock`.
  Версии зависимостей закреплены `Chart.lock` и `chart-deps.sha256` (дата и источник —
  `docs/evidence/2026-11-13-team-analytics-test-stack.md`); архив с другим хешем — отказ.
- Проверка политик (`run.sh check-policies`, часть `up` сразу после `port-forward`): стенд
  забирает бандл политик, который сервер отдаёт OPA (`/api/auth/rules`), и проверяет
  `issues.rego` и `comments.rego` каждый отдельно: в архиве не должно быть ничего, кроме
  обычных файлов и каталогов (ссылка где угодно — отказ), и двух записей, чьи имена после
  нормализации совпадают (`rules//issues.rego` — это `rules/issues.rego`); файл должен совпадать с файлом импорта
  байт в байт (`verify/policy_bundle.sh check`) и содержать отметку патча
  `Local patch (role floor)`. Если хоть одна из двух политик стоковая — отказ.
- Обратный прокси `ta-proxy` (`proxy.yaml`): `/api`, `/admin`, `/static`, `/django-rq`,
  `/profiler` — бэкенд CVAT (в том числе `/api/team-analytics/`); `/analytics` — Grafana за
  проверкой доступа CVAT; всё остальное — UI. Адрес: `http://localhost:<TA_HOST_PORT>` через
  `kubectl port-forward`.
- Проверка воркера аналитики (`run.sh check-worker`, часть `up` сразу после `port-forward`):
  команда его liveness-пробы (`django-admin workerprobe team_analytics --expected-num-workers
  <NUMPROCS>`) в его поде — все процессы очереди зарегистрированы; число перезапусков, события
  `Unhealthy` и журнал воркера (в каталоге состояния, `worker.log`).
- Учётные записи (`accounts.json`, пароль `TA_SEED_PASSWORD`; в под бэкенда он передаётся
  через стандартный ввод скрипта загрузки, не в командной строке): администратор `ta-admin`;
  организация `ta-org-a` с владельцем `ta-owner`, `ta-maintainer`, `ta-supervisor`,
  `ta-worker`; `ta-outsider` не состоит нигде; организация `ta-org-b` с владельцем
  `ta-owner-b` и `ta-maintainer-b`; `ta-org-c` и `ta-org-v` итогового прогона (ниже);
  организация `ta-org-s` проверки настроек с `ta-owner-s`, `ta-worker-s` и `ta-worker-s2`.
  После загрузки каждая роль читается обратно через API. Затем загрузка задаёт список
  технических учётных записей (Technical accounts) равным `TA_TECHNICAL_ACCOUNTS` из `stack.env`
  (имена через запятую или пробел, по умолчанию `ta-bot`): `ta-admin` находит id каждого имени
  поиском настроек (`GET /api/team-analytics/settings/users?search=<имя>`, точное совпадение
  имени), отправляет `PUT /api/team-analytics/settings` с этими id и читает список обратно
  (`GET /api/team-analytics/settings`), иначе отказ. Если список уже такой, ничего не
  отправляется: повторный `up` или `seed` его не меняет (и не сдвигает поколение ответов).
- Проверка события: `ta-worker` отправляет клиентское событие через `POST /api/events`, и
  стенд ждёт его в таблице `events` ClickHouse вместе с новым полем payload.
- Проверка рабочего времени (`run.sh check-tracer`, часть `up`): владельцы организаций
  создают через API проект `ta-tracer` с задачей и заданиями, исполнители отправляют
  события в своих заданиях (`ta-worker` 90 мин и `ta-supervisor` 30 мин в `ta-org-a`,
  `ta-maintainer-b` 60 мин в `ta-org-b`; `stack_api.py`, `WORK`). Обновление никто не
  запускает: стенд ждёт, пока его выполнит периодическая задача, сверяет цифры
  `/api/team-analytics/overview` у администратора (`ta-org-a`, `ta-org-b` и весь экземпляр) и
  отказы для каждой роли по точному телу ответа (владельцам, мейнтейнерам, супервайзеру,
  исполнителю и постороннему — 403 с телом DRF `{"detail": ...}` с организацией и без неё,
  без входа — 401). Затем отметка обновления в ответе `status`
  (`refresh.last_success_at`) должна дважды сдвинуться, пока контейнер воркера не
  перезапускался; журнал воркера стенд не читает. Наконец `browser_check.cjs` в headless Chrome
  входит как `ta-admin` с выбранной `ta-org-a` (ссылка в шапке, цифры организации на странице)
  и как `ta-owner`, `ta-maintainer` и `ta-worker` (ссылки нет, прямой переход — «not
  available», запрос к API — 403). `TA_SCREENSHOT_DIR` сохраняет снимки экрана.
- Ответы аналитики. Ответ, которого нет в кэше, сервер ставит в очередь воркера и ждёт до
  5 с; не дождавшись, отвечает 429 с `Retry-After`. Все клиенты стенда на 429 спрашивают снова:
  проверки на Python — в пределах `TA_ANALYTICS_RETRY_S` (30 с, `stack_api.get_json`), страница
  — средствами cvat-core (три повтора). Ответ кэшируется по поколению итогов, которое двигает
  только шаг обновления, записавший итоги; проверки, которые меняют итоги прямо в ClickHouse
  или останавливают воркер, сами сдвигают поколение через кэш Django в поде сервера
  (`stack_ops.py`), иначе они прочли бы ответы, сохранённые до изменения.
- Проверка прогресса задач (`run.sh check-task-progress`, часть `up` после проверки рабочего
  времени; `task_progress.py`, `task_progress_browser.cjs`). Сначала стенд убеждается, что UI
  работает на образе `TA_UI_IMAGE`. Затем `ta-admin` в личном пространстве создаёт через API
  две новые задачи: в первой по одному заданию на каждую пару этапа и состояния (этапы и
  состояния сверяются со схемой API сервера), во второй одно задание annotation / new.
  Каждое задание читается обратно. Headless Chrome входит как `ta-admin` и открывает список
  задач с фильтром по этим задачам. На карточке каждой задачи проверяются подписи легенды
  со счётчиками, цвет, вес и подсказка каждого сегмента (таблица UI-2 в
  `docs/fork-specification.md`) и общее число заданий. Проверяется, что нет корзины
  «not available» и стоковых подписей. Текст легенды должен читаться на карточке
  (контраст не ниже 4.5:1).
- Итоговый прогон (`run.sh check-final`, последняя часть `up`; `final_run.py`,
  `final_browser.cjs`). Организация `ta-org-c` (`ta-owner-c`, `ta-worker-c` и
  техническая учётная запись `ta-bot`, которую загрузка внесла в список,
  `TA_TECHNICAL_ACCOUNTS`). Цифры API и страницы читает `ta-admin` с выбранной организацией. На каждом запуске
  создаётся новый проект, и `ta-worker-c` в headless Chrome работает в его задании:
  рисует, перетаскивает, вставляет, размножает, меняет класс, удаляет, листает кадры и
  сохраняет. Ещё он дважды запускает детектор из AI tools: сначала модель ничего не
  возвращает, затем две рамки и полигон. Функции модели на стенде нет, поэтому в браузере
  подставляются только список моделей (`HEAD` и `GET /api/lambda/functions`) и ответ модели
  (`POST /api/lambda/functions/<id>`); запись детектора отправляет сам UI. Каждая новая
  запись ищется в ClickHouse. `ta-bot` сохраняет рамки через API.
  Затем сверяются цифры API аналитики и страницы. В `ta-org-v` (`ta-owner-v`) один раз
  загружается синтетическая работа: 100 исполнителей, 40 проектов с длинными
  именами, десять недель истории. Исполнители — настоящие учётные записи (их и членство
  в организации создаёт тот же `seed_users.py`), у каждого своё задание. Текущую неделю
  каждый исполнитель отправляет сам, войдя в CVAT: записи клиента идут через
  `POST /api/events` и Vector, рабочее время из них считает CVAT, рамки исполнитель
  сохраняет в своём задании. Старые недели вставляются прямо в ClickHouse: API сдвигает
  время записи на разницу между временем получения и временем отправки, а рабочее время и сохранённые рамки
  CVAT записывает временем их получения. Повторный запуск догружает только недостающее
  (`run.sh load-volume`); `TA_VOLUME_ORG` задаёт другую организацию. По ним сверяются
  цифры, тренды и длина страницы,
  проверяются фильтры, полный вид, сравнение и узкое окно. Затем каждая учётная запись
  обращается к каждому эндпоинту аналитики: администратору 200 (весь экземпляр и каждая
  названная организация), всем остальным, включая `ta-bot`, владельцев и мейнтейнеров, — 403.
  Наконец воркер аналитики масштабируется до нуля,
  поколение итогов сдвигается (ни один ответ не взят из кэша), и стенд проверяет панель ошибки
  страницы (после повторов cvat-core) и то, что разметка рисуется и сохраняется; после этого

  ClickHouse стенда: основные операции проходят, эндпоинты отвечают в пределах, а цифры недели
  `ta-org-a` и организации объёма возвращаются сами, равными прежним, после того как
  очередной запуск обновления создал схему и история пересчитана (печатается, через сколько
  секунд); cutover должен остаться прежним без вмешательства. `check-load` (на данных объёма):
  по 100 последовательных запросов `GET /api/tasks` и разметки задания организации объёма —
  исходный p95; затем три залпа по двенадцать одновременных обзоров с разными параметрами
  (каждый — промах кэша) с выборкой тех же двух адресов, сначала каждый залп в момент, когда
  взята блокировка обновления, потом пока заполняется история (дни старше недели помечаются к
  пересчёту, как это делает ежедневная проверка). Судится: все обзоры — 200 с цифрами в
  пределах бюджета клиента (4 × ожидание + 3 × Retry-After из настроек сервера, 29 с по умолчанию; с повторами после 429), p95 под нагрузкой не больше
  1,5 × исходного p95 + 25 мс; печатаются сырые числа и память воркера и ClickHouse.
  `check-review`: исправления ревью — параметр, которого обзор не читает (`search`, `cachebust`), отвечается из
  кэша без задания воркеру; слишком длинные `tz` и `month` — 400 от API сразу, неверный `period` — 400 от воркера;
  `Cache-Control: no-store` у 401, 403, 404 и 429; поколение итогов — целое число (без счётчика начинается со
  времени в секундах), растёт ровно на один за запуск, который записал, и не меняется за запуск, которому нечего
  делать (сверяется с журналом воркера раз в 2 с); копии задачи обновления, накопившиеся при воркере на нуле,
  первый запуск убирает. `check-load`
  ещё сверяет журнал воркера (окно с запасом в две минуты до начала залпа): каждое чтение залпа
  выполнено один раз; второй раз — только если между его первым и вторым началом закончился запуск
  обновления, который записал (он сдвигает поколение, и ответ, посчитанный во время записи,
  считается снова), — такой повтор печатается с обоими временами и строкой запуска; три выполнения
  и повтор без такого запуска — отказ, и каждое условие судится только по своим залпам; поколение
  сдвинулось раз за запуск, а
  `check-isolation worker-down` считает подключения сервера к Postgres, пока ждут двенадцать запросов.
  Во время залпов `check-load` раз в 2 с записывает число подключений к Postgres (все клиенты,
  `pg_stat_activity`) и занятую память Redis в памяти (`INFO memory`, `used_memory`), печатает
  максимум и минимум. `TA_LOAD_HEAVY=1 run.sh check-load` — тяжёлая конфигурация: релиз
  обновляется на месте с ClickHouse в 4 CPU (`clickhouse.resources.limits.cpu=4` вместо 2),
  объём загружается ещё в `ta-org-v2` и `ta-org-v3` (те же исполнители, втрое больше данных),
  залпы читают весь экземпляр (`TA_LOAD_SCOPE=instance`), пределы те же; после — релиз
  возвращается к значениям стенда, и при отказе тоже.
  `check-isolation redis-down` (и последняя часть `check-isolation` без части): Redis в памяти
  (`statefulset/cvat-redis-master`: очереди rq, блокировка обновления, кэш Django) на нуле;
  шесть раз по два чтения (обзор, которого нет в кэше, и `status`) — каждое 503
  `{"error": "unavailable"}` (не 500) в пределах ожидания чтения плюс 2 с. Затем Redis
  возвращается, стенд ждёт выката сервера и воркеров, проверяет расписание обновления
  (`team_analytics_refresh` в `rq:scheduler:scheduled_jobs`; если его нет, восстанавливает
  командой `django-admin syncperiodicjobs` в поде сервера, как это делают инициализатор и
  точка входа бэкенда) и ждёт нового обновления и цифр недели `ta-org-a`. Её запускают
  последней: она перезапускает всё, что зависит от Redis.
  `check-analytics-off`: релиз переустанавливается в том же пространстве имён с
  `analytics.enabled=false`; сервер отвечает, воркера аналитики нет, обновление не
  запланировано, `/api/team-analytics/*` — 404 (запросы идут через `port-forward` прямо на
  Service бэкенда: nginx прокси называет Grafana, которой без аналитики нет). Стенд остаётся
  таким; после проверки — `down`.

- Доказательства тикета 09 (`run.sh check-evidence STEP`, `evidence.py`, не входит в `up`; на
  проверочном стенде со своим `TA_RUN_ID` и портом 8491, где `up` прошёл). Каждый шаг печатает, что
  ожидал и что увидел, `[evidence] PASS` или `FAIL`, и при расхождении завершается с ошибкой.
  `rq-start-race` (только чтение): реестр упавших заданий очереди `team_analytics` с момента старта
  пода воркера, для каждого id — его собственная запись (`status`, есть ли `exc_info`) и строки
  журнала: процесс, чистящий реестры («Cleaning registries»), объявляет упавшим задание, которое
  другой процесс как раз готовит к выполнению («Handling failed execution» и «Preparing for
  execution»; `clean_intermediate_queue` rq 1.16.0). Запись без таких строк — отказ; если записей
  с этого старта нет, гонка не случилась, и это печатается.
  `liveness`: `supervisorctl stop` одного процесса rq в поде воркера (процесс снимается с учёта в
  Redis и не перезапускается), проба живости (`django-admin workerprobe team_analytics
  --expected-num-workers N`, по процессам этого пода) перестаёт проходить, kubelet перезапускает
  контейнер; печатаются число перезапусков до и после и события `Unhealthy`; команда пробы после
  выката должна снова пройти (код 0) в пределах 90 с, иначе отказ.
  `killed-worker`: процесс сервера ClickHouse останавливается (`SIGSTOP`), запрос обзора, которого
  нет в кэше, ставит задание чтения, оно начинается и ждёт ClickHouse; процессы rq пода воркера и
  их потомки (рабочий процесс задания) убиваются (`SIGKILL`). Находятся они по командной строке
  (`rqworker`), а если не нашлось ни одного — по pid, которые реестр воркеров rq в Redis хранит
  для этого пода; печатается, каким способом. Ни одного убитого процесса — отказ; через 3 с ни
  один из них не должен работать (нет в `/proc` или зомби). ClickHouse продолжается (`SIGCONT`).
  Тот же запрос повторяется: до ответа только 429, затем 200; ответ не раньше предела брошенного
  задания (`2 × TEAM_ANALYTICS_READ_JOB_TIMEOUT_S + 120`, 300 с по умолчанию, минус 15 с) от
  первого запроса и не позже этого предела, ожидания чтения и минуты от убийства; в журнале
  воркера два выполнения задания (убитое и поставленное снова; журнал читается и у предыдущего
  контейнера пода, если проба живости перезапустила его в это время). Время ответа берётся в
  момент прихода 200, до чтения журналов. Печатаются состояния записи
  задания и строки журнала воркера с его id. Значение чарта не меняется (таймаут по умолчанию,
  шаг идёт до пяти минут).
  `idle-generation` (меняет чарт): релиз обновляется на месте с
  `TEAM_ANALYTICS_REFRESH_INTERVAL_S` = 600, и шаг сначала читает из сервера, что действует именно
  600; после запуска, который записал, шесть минут запусков без работы: поколение не меняется
  (читается раз в 15 с), в журнале воркера не меньше пяти запусков, ни один не записал. Затем
  релиз возвращается к значениям стенда.
  `two-replicas` (меняет чарт): `cvat.backend.worker.teamAnalytics.replicas=2`; оба пода готовы,
  двенадцать одновременных чтений, которых нет в кэше, — 200 в пределах бюджета клиента, чтения
  выполняли оба пода; за двенадцать минут (запуск раз в минуту; запуск пишет, когда начало
  прошлого обновления старше интервала стенда 60 с, так что пишет от каждого второго до каждого)
  не меньше пяти запусков, которые записали, из них хотя бы один на каждом поде;
  каждый начатый запуск прочитан из журнала с началом и концом (кроме одного ещё идущего на под),
  строка без разбираемого времени — отказ; запуски, которые записали, на двух подах не
  пересекаются по времени (блокировка). Если не выполнено только «хотя бы один на каждом поде»
  (всё остальное в порядке), сообщение об отказе говорит об этом прямо: шансы самого шага это
  допускают (около одного к тридцати двум), шаг стоит повторить, прежде чем искать дефект. Затем
  снова одна реплика.
  `off-then-on` (меняет чарт): снимок списка технических учётных записей и таблицы
  `team_analytics_technicalaccount` (Postgres), затем `check-analytics-off` (аналитика выключается
  обновлением на месте) и включение обратно; `helm history` после каждого шага — новая ревизия с
  «Upgrade complete», не переустановка. После включения таблица и список такие же, расписание
  обновления вернулось, цифры недели `ta-org-a` вернулись. Если шаг упал или прерван до
  включения, аналитика включается обратно и `port-forward` снова идёт на прокси.
  Порядок одного прогона доказательств: `up`, затем `check-evidence rq-start-race` (сразу после
  старта воркера), `liveness`, `killed-worker`, `idle-generation`, `two-replicas`,
  `TA_LOAD_HEAVY=1 check-load`, `off-then-on`, `check-isolation redis-down` последним. Значения
  чарта меняют `idle-generation`, `two-replicas`, тяжёлый `check-load` и `off-then-on`; каждый
  возвращает их сам, в том числе при отказе и прерывании (`off-then-on` — включением аналитики
  обратно): ловушка `EXIT` запускает `run.sh restore-chart` отдельным процессом. Он сначала
  откатывает релиз, оставленный прерванным `helm upgrade` в состоянии `pending-*` (`helm
  rollback` к прежней ревизии), затем обновляет его к значениям стенда с аналитикой, ждёт
  готовности и снова запускает `port-forward` на прокси. Если и это не удалось, печатается
  команда, которую нужно выполнить вручную из корня репозитория (`... run.sh restore-chart` с
  переменными этого стенда).

Рендер чарта (с CRD из каталогов `crds/` чартов) и манифесты прокси проверяются на каждом
запуске как объекты, которые создал бы Kubernetes, до применения:
`kubectl` разбирает каждый документ, YAML или JSON, и раскрывает списки, `render_guard.py`
судит. Отказ установки: вид, который кластер не называет видом пространства имён (кластерные
объекты, CRD, неизвестные кластеру виды), объект в чужом пространстве имён, поле `image` в
любом месте объекта с образом вне списка, без тега или с тегом `latest`, `imagePullPolicy`
кроме `IfNotPresent` и `Never`, серверный образ, отличный от образа форка; из путей на узел или
наружу — только эти: Service другого типа, чем `ClusterIP` (headless тоже `ClusterIP`), или с
внешними адресами, и ключи на любой глубине любого объекта: сеть, PID или IPC узла, порт узла,
том `hostPath`, привилегированный режим, добавленные capabilities (ключ с таким именем в другом
месте, например ключ `hostPath` в данных ConfigMap, тоже даёт отказ — ложный, оставлен); прочие
настройки безопасности контейнера, например `allowPrivilegeEscalation: true`, не проверяются;
RoleBinding на ClusterRole или на субъект, отличный от
ServiceAccount этого пространства имён. Выход к томам и маршрутам других проектов
проверяется по разрешённому списку — разрешено то, что есть в настоящем рендере, остальное
отказ: у тома пода источник только `configMap`, `emptyDir`, `persistentVolumeClaim` или
`projected` (внутри `projected` — только `configMap`); поле `volumeName` (заявка на
конкретный том) нигде; Ingress нет вовсе (адрес стенда — прокси за `port-forward`); объекты
Endpoints и EndpointSlice не
допускаются вовсе (их пишет сам кластер для Service с селектором); Secret только типов
`Opaque`, `generic` или без типа. В рендере должен быть ровно один Deployment воркера
аналитики (метка `component: worker-team-analytics`, аргументы `run worker team_analytics`);
рендер с `analytics.enabled=false` проверяется так же и не должен содержать ни одного объекта
воркера. Проверки выхода на узел и RoleBinding по-прежнему отказывают по списку. Не
проверяется и заявка
(или шаблон заявки), которая привязывается к существующему тому, не называя его: с
селектором по меткам, с источником данных или с пустым классом хранения; в настоящем
рендере таких нет. Так ни
кластерных видов, ни перечисленных путей к узлу, к чужим томам и маршрутам в проверенном нет;
что проверяется только рендер, сказано дальше. Проверяется рендер
`helm template`, а не то, что установит `helm upgrade --install`: шаблоны чарта и его
зависимостей обращаются к `.Capabilities` и `lookup`, которые при установке видят кластер, так
что установленные объекты могут отличаться от проверенных. Хранилище —
класс по умолчанию. `down` удаляет пространство имён целиком, включая тома, которые чарт
помечает к сохранению, и останавливает только свой `port-forward` (PID и время старта; учёт
хранит ещё и порт).
