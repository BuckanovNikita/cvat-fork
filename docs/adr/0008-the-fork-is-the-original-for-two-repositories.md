# The fork is the original for two repositories: its own two charts, and builds parameterised for a closed network

Until 2026-11-16 the fork owned the source and the two images, and took its model-serving part from a public chart repository: `helm-chart/Chart.yaml` listed `nuclio/nuclio` at the `0.22.*` line as a dependency, gated by `nuclio.enabled`. A deployment that had to run the same chart inside a closed network shipped a second copy of that chart beside the main one and deployed it as its own release instead, so one component had two definitions and which one a deployment used depended on which file the release pointed at. The build had the same shape: `Dockerfile.server` began from `python:3.12-slim-bookworm` and `Dockerfile.ui` from `node:lts-slim`, named github.com and PyPI in their steps, and `build-ui.sh` rewrote the Node base through a BuildKit `--build-context`; a build inside the perimeter meant editing the files the fork publishes.

On 2026-11-17 the owner decided that the fork is the original for two repositories: it owns the source, both image builds, both charts and their assets, and a downstream repository vendors a defined subset of them. There are two charts, each installed on its own release: `helm-chart/`, the CVAT deployment, and `helm-chart-nuclio/`, nuclio, whose templates are upstream's and whose images, registries and dashboard host come from `helm-chart-nuclio/values.yaml` alone. The main chart no longer depends on nuclio. `nuclio.enabled` now only turns on the server's serverless settings (`CVAT_SERVERLESS`, `CVAT_NUCLIO_HOST`) in `helm-chart/templates/_helpers.tpl`, and the dashboard host a deployment reaches is a value on both sides. The main chart's dependencies are committed as tarballs — `helm-chart/charts/`, locked by `helm-chart/Chart.lock` — and the nuclio chart has none, so `helm template` of either chart needs neither network nor a chart repository.

Every input a closed network has to supply is a build argument with a public default, so the same files build inside and outside it and nothing of that network is committed. In `Dockerfile.server`: `BASE_IMAGE`, `RUST_IMAGE` and `GOLANG_IMAGE` for the three bases, and `APT_REMOTE`, `APT_SECURITY_REMOTE`, `PIP_INDEX`, `GO_PROXY`, `CARGO_INDEX` and `GITHUB_PROXY` for the mirrors and indexes. In `Dockerfile.ui`: `NODE_IMAGE`, `NGINX_IMAGE` and `NPM_REGISTRY`. An empty value sets nothing at all, so the base image's own configuration or the tool's public default stands. `build-server.sh` and `build-ui.sh` read the same names from their environment and pass on only those that are set. A base is a reference, not a digest: a tag is accepted, and `build-server.sh` pulls each base and records in its log the digest the reference resolved to, once per pull and once more in the summary line.

The fork also fixes which files the downstream repository holds: `Dockerfile.server`, `Dockerfile.ui` and `Dockerfile.ui.dockerignore`, `build-server.sh` and `build-ui.sh`, `.dockerignore`, `.yarnrc.yml`, `package.json`, `yarn.lock`, the backend entry points (`manage.py`, `rqscheduler.py`, `wait_for_deps.sh`, `backend_entrypoint.sh`, `backend_entrypoint.d/`), `supervisord/`, `components/`, `cvat/`, the five frontend packages (`cvat-core/`, `cvat-data/`, `cvat-canvas/`, `cvat-canvas3d/`, `cvat-ui/`) and both chart directories. The downstream re-copies that set from a fork revision instead of merging the fork's history. Equality is behavioural, not byte for byte: the same files render and build the same deployment, with the downstream's own values file and CI on top, and a hand edit or a hash gate is not part of the arrangement.

## Considered Options

- **Vendoring the nuclio chart downstream and leaving it a public dependency in the fork.** The fork would stay closer to upstream. Rejected: the copy that overrides a dependency is what gave the component two sources; the deployment would own a chart the fork's own chart still names, and a nuclio version bump would be made twice.
- **One chart, with nuclio vendored under `helm-chart/charts/` as a tarball.** Nothing new to install. Rejected: a tarball is the published chart, reachable through its values only, and the deployment installs nuclio as its own release with its own registry settings — which a dependency of the main release cannot be.
- **Keeping the corporate values in the chart, as defaults.** One file to change per deployment. Rejected: the fork's remote is public, so a default naming a corporate host or registry leaks it, and the chart would serve one network only.
- **Pinning base images by digest, as ADR 0007 said.** Reproducible by construction. Rejected by the owner: a mirror that serves a re-pushed copy has a digest of its own, so the pin would be edited for every build inside the perimeter, and the public image's digest says nothing about the copy actually pulled. The log records the resolved digest instead.
- **Leaving the perimeter to a committed registry file or a build-time edit of the tree.** The Dockerfile stays plain. Rejected: the file would name a host, and the tree that builds inside the network would not be the tree that builds in public.

## Consequences

- **The fork's chart and build files are a compatibility surface for another repository.** Renaming a value in `helm-chart/values.yaml` or `helm-chart-nuclio/values.yaml`, a file in the shared set, or a build argument in either Dockerfile or either build script, is a breaking change downstream and not a local edit: the downstream re-copies the set and its values and CI refer to these names. Such a rename is made with the downstream's change in the same breath.
- The fork publishes nothing corporate. No host, registry path or credential appears in either chart, in either Dockerfile or in either build script; a deployment supplies them through its own values file and its CI, and an unset argument leaves the public default.
- The main chart renders no nuclio objects. An installation that wants model functions installs `helm-chart-nuclio/` as its own release beside `helm-chart/`, and the `nuclio.enabled` switch and the dashboard host have to agree on both sides.
- `helm-chart/Chart.yaml` is edited by the fork now, for the removed nuclio dependency and the committed tarballs, so a release that changes it conflicts; the resolution keeps the fork's dependency set and re-copies a tarball when upstream's version line moves. `helm-chart-nuclio/` is upstream nuclio's templates copied, so a nuclio version bump is a manual re-copy with a review of its values, not `helm dependency update`.
- The amendments of [ADR 0003](0003-kubernetes-only-with-the-upstream-helm-chart.md) that say the chart dependencies are "still fetched and pinned as before" no longer hold: the dependencies are the committed tarballs under `helm-chart/charts/`.
- [ADR 0007](0007-the-fork-builds-its-images-from-public-bases-the-server-on-debian-12.md) is amended: its bases still default to the public Debian, Rust and Go references, but "public bases" now means the defaults rather than the only possibility, and its "pinned by digest" no longer describes the build.
- The build's audit trail is its log. A tag can move, so the server build prints the digest each base reference resolved to, and the UI build prints the base it was built on; no digest has to be known before the build starts.
- A fork update that touches the shared set needs the downstream's re-copy in the same release, and the fork cannot tell whether it happened. The downstream dates its re-copy by the fork revision it took, which is the record of what is deployed.
- Upstream's own `Dockerfile` is untouched and still in the tree. The fork has no werf project: `build-server.sh` and `build-ui.sh` are its only build entry points, and whatever orchestrates a deployment — helm by hand or a CI — belongs to the repository that deploys.
